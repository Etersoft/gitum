# gitum 2: разработка параллельно апстриму

Статус: черновик для обсуждения, 2026-11-11.

Решение: развиваем gitum, даже если от текущего кода останется одно название.
Главная идея — вести свои изменения параллельно апстриму и синхронизироваться
с ним удобно и наглядно: в любой момент видно, где каждое наше изменение
находится относительно апстрима.

Требования собраны из трёх сценариев:

- **wine-rebased (робот).** Стек слоёв winehq → rebased (wine-staging) →
  rebased-basealt → rebased-etersoft. Обновление по cron на следующий тег.
  Цепочка разрешения конфликтов rerere → правила → агент. Ревью через
  candidate/*. Отчёты в eterbug. Экспорт в RPM.
  См. `wine-rebased-utils/rebased/update-rebased-algorithm.md`.
- **wine-kloder (серии для апстрима).** Около 100 серий, у каждой своя ветка от
  winehq/master. Внутренний MR, потом MR в WineHQ строго по одному. Одна серия
  живёт в двух вариантах (master и rebased-etersoft). Апстрим принимает
  патчи с правками. Работают несколько сессий в разных worktree.
- **ALT packaging.** Судьба каждого изменения (PR, принят в релиз X,
  исправлен иначе, только для дистрибутива). Прыжок на релизный тег.
  Экспорт в PR с перераскладкой путей и бэкпорт с `Origin:`. Несколько
  апстримов в одном репо (vendored). Gear/rpmgs.

## 1. Что gitum умеет сейчас (0.9.0)

- Python 3, GitPython 3, сборка через pyproject, 52 теста на pytest.
- Код возврата 1 при ошибке. Понятная ошибка «не gitum-репозиторий».
- Файлы состояния лежат в `git_dir`, а не в захардкоженном `.git/`.
- Двоичные файлы, CRLF и не-UTF-8 переживают перенос (`git am --keep-cr`).

Модель прежняя: один слой патчей над одним апстримом, ветки
`upstream`/`rebased`/`mainline`/`patches`. `merge` по-прежнему переносит
апстрим **по одному коммиту**.

По-прежнему нет:
- блокировок и работы в linked worktree (gitum делает `checkout -f`,
  `reset --hard`, `clean -d -f` в рабочем дереве пользователя);
- машиночитаемого вывода;
- серий, метаданных, отслеживания судьбы патчей;
- работы с forge.

`update` без `--message` открывает редактор.

**Что переиспользуем:**
- идею журнала-orphan-ветки (`patches`): набор `*.patch` плюс sha базы,
  история ветки = история состояний;
- идею линейной истории `mainline`, где `git log -p` и bisect работают
  между нашими состояниями;
- создание коммитов без рабочего дерева (`hash-object`/`mktree`/`commit-tree`);
- побайтовую работу с диффами;
- тестовые фикстуры;
- каркас CLI.

Движок переноса пишется заново.

## 2. Чему учимся у wine-staging

wine-staging — работающий пример: около 120 серий параллельно апстриму,
около 1800 коммитов «Rebase against SHA».

- **Серия — каталог** `patches/<серия>/`: `definition` плюс `0001-*.patch`.
  В `definition` строки `Fixes: [bug] описание`, `Depends: <серия>`,
  `Disabled: true` (с комментарием-причиной), `Helps:`. Раньше были ещё
  `IfDefined` и `Apply-After`.
- **База** — `staging/upstream-commit`, один sha wine на весь набор.
- **Сборка** — `patchinstall.py`: применяет серии с учётом `Depends`,
  `--all`/`-W`, бэкенды `git am`/`git apply`/`patch`. Отключённые серии
  пропускаются, зависимость на отключённую серию — ошибка.
- **Процесс.**
  - Ребейз почти ежедневно, на вершину master, а не на тег:
    `commit-rebase.sh` записывает sha и коммитит «Rebase against SHA».
  - Принятые апстримом серии удаляются руками в коммите ребейза
    («Removed patchset fixed upstream»).
  - Сломанные серии получают `Disabled: true`.
  - Релиз — `commit-release.sh X.Y`: тот же sha, `staging/VERSION`
    («Wine Staging X.Y»), коммит «Release vX.Y» и тег `vX.Y`.
  - `precommit-hook.sh` не даёт закоммитить неподготовленные изменения
    в `staging/` и `patches/`.
- **История репозитория = история состояний набора** — ровно идея gitum-ветки
  `patches`, только по сериям.

**Чего им не хватает:**
- связи серии с MR и багами (кроме `Fixes`);
- автоматического определения принятия, тем более с правками;
- вариантов серии на разных базах;
- журнала разрешения конфликтов;
- машиночитаемого отчёта;
- работы в git-ветках: патчи правят как файлы, а серию собирают в дереве
  wine, чтобы проверить.

**Что берём:** формат каталога серии и `definition` (совместимо: gitum умеет
импортировать и экспортировать staging-раскладку), граф `Depends`, базу как
явный sha, `Disabled` как состояние серии, коммит журнала на каждое состояние.

**Что добавляем:** серия живёт как git-ветка (работают обычными git-средствами),
а каталог в журнале генерирует gitum. Плюс метаданные, варианты на базах,
отслеживание принятия, журнал конфликтов.

## 3. Модель

```
upstream (источник)  winehq: remote + ref + шаблон релизных тегов [+ prefix]
   │
series (серия)       именованный упорядоченный набор изменений + definition
   │                 + метаданные; может зависеть от других серий
   │
variant (вариант)    серия, материализованная на конкретной базе:
   │                 series/<имя>@master, series/<имя>@etersoft
   │
layer (слой)         ветка = база (upstream или другой слой) + список серий
                     (+ «прочие» коммиты, пока не разобранные по сериям)
change (изменение)   один коммит; постоянная идентичность через trailer
                     Gitum-Id; своя судьба (fate), если отличается от серии
```

- **Слой** решает задачу робота: `rebased-etersoft` = база `rebased-basealt` +
  сотни коммитов. Сначала эти коммиты можно не раскладывать по сериям
  (неявная серия `_unsorted`), раскладывать постепенно.
- **Серия** решает задачу wine-kloder и staging: у неё есть база (обычно
  upstream master), зависимости, MR, статус, очередь.
- **Изменение** решает задачу ALT: судьба каждого патча.

**Идентичность.**
- Trailer `Gitum-Id: <короткий id>` добавляется при `gitum save` или хуком
  commit-msg и сохраняется при переносе.
- При экспорте в апстрим trailer вырезается. Связь «коммит в апстриме ↔
  изменение» хранится в журнале (patch-id плюс найденный sha), а не в
  сообщении коммита.
- Дополнительные trailer'ы `Eterbug:`, `Bug:`, `Origin:` переносятся в
  метаданные.

**Судьба (fate) изменения или серии:**
- `local` — только у нас, без причины;
- `draft`;
- `review` — внутренний MR;
- `queued`;
- `sent` — MR апстрима, версия vN;
- `merged` — sha и первый релиз;
- `merged-modified` — sha, сходство;
- `rejected`;
- `fixed-differently` — ссылка;
- `distro-only` — причина;
- `backport` — `Origin`, удалить на релизе X;
- `disabled` — причина;
- `dropped` — кем и когда.

## 4. Хранение: журнал

Журнал — append-only ветка `gitum/journal` (имя настраивается). Каждый коммит —
опубликованное состояние. Раскладка дерева совместима со staging:

```
gitum.toml                     конфигурация проекта (общая для всех клонов)
upstreams/<имя>                sha базы, тег, дата
series/<имя>/definition        Fixes/Depends/Disabled (staging) + наши ключи
series/<имя>/0001-*.patch      патчи серии (format-patch от её базы)
series/<имя>/meta.json         MR, баги, fate, варианты, принятые sha
layers/<имя>.json              база (sha), вершина (sha), серии по порядку,
                               series-файл: Gitum-Id, patch-id, subject
changes.json                   Gitum-Id → fate, upstream-коммит, релиз, PR
runs/<дата>-<id>/report.json   отчёт переноса: классификация, кто и как
                               разрешил конфликты, range-diff
rr-cache/                      общий rerere (объединение всех клонов)
```

**Зачем так:**
- Серия — отдельный каталог. Две сессии, правящие разные серии, создают
  коммиты журнала, которые сливаются трёхсторонним merge без конфликтов.
  Это и есть параллельная работа без force-push.
- Журнал только дописывается: публикация fast-forward, force-push не нужен.
- Линейная ветка истории на слой `gitum/history/<слой>` (обобщение `mainline`).
  Каждый коммит — `commit-tree <tree вершины слоя> -p <предыдущий>`, поэтому
  `git log -p` и bisect работают между нашими состояниями. Дешевле, чем
  в v1: патчи не накладываются, дерево берётся готовое.
- Ветки слоёв и вариантов переписываются, как сейчас (`rebased-*`). Их
  публикация с force остаётся, но журнал и история — источник истины,
  и из журнала всё восстанавливается (`gitum checkout`).
- Совместимость с роботом: теги `<слой>-START` и версионные ветки
  `rebased-*-X.Y` gitum может выставлять сам (опция `compat`).

## 5. Конфигурация (`gitum.toml` в журнале)

```toml
version = 2

[upstream.winehq]
remote = "winehq"
url = "https://gitlab.winehq.org/wine/wine.git"
ref = "master"
release-tags = "wine-*"          # «первый релиз, содержащий коммит», --next-release
# prefix = "third-party/rocksdb" # vendored-апстрим внутри дерева (ALT)
# import = "tarball"             # база из rpmgs-импорта (gear)

[layer.rebased]                  # слой, собираемый из серий staging
base = "upstream:winehq"
branch = "rebased"
series-from = "staging"          # серии импортированы из wine-staging
version-file = "VERSION"

[layer.basealt]
base = "layer:rebased"
branch = "rebased-basealt"
compat-start-tag = "rebased-basealt-START"

[layer.etersoft]
base = "layer:basealt"
branch = "rebased-etersoft"
annihilate-reverts = true

[series]
default-base = "upstream:winehq"
variant-branch = "series/{name}@{base}"
subject-lint = '^[a-z0-9_./-]+: [A-Z].*\.$'   # «module: Description.»
strip-trailers = ["Co-Authored-By", "Gitum-Id"]

[queue]
one-at-a-time = true             # не больше одной серии в состоянии sent

[resolve]
chain = ["rerere", "rules", "agent"]
rules = "tools/conflict-resolve.py"
agent = "tools/conflict-agent.sh"
review-unless = ["rerere"]       # всё прочее — через candidate/*

[publish]
remote = "origin"
candidate-prefix = "candidate/"
check = "./build.sh"             # сборка до публикации

[forge.winehq]                   # плагин или внешний хук
type = "gitlab"
url = "https://gitlab.winehq.org"
fork = "lav/wine"

[hooks]                          # JSON события на stdin
change = "tools/notify-bugs.py"
run = "tools/notify-telegram.sh"
```

Формат TOML читается стандартным `tomllib`, требуется Python ≥ 3.11.

## 6. Команды

Общее для всех команд:
- `--json` для машиночитаемого вывода;
- `--repo`;
- никаких интерактивных вопросов: где нужен ввод, команда завершается
  с кодом 2 и сообщает, что именно нужно.

| Команда | Что делает | Для кого |
|---|---|---|
| `gitum init` / `gitum import` | Создать журнал из существующих веток: слои по `-START` тегам, каталог staging, quilt/spec. | все |
| `gitum status` | Дерево: апстримы → слои → серии. Для каждого узла: база, отставание от апстрима, число патчей, незавершённый перенос (на каком патче), расхождение вариантов, кто держит блокировку. Плюс таблица изменений: изменение → судьба → нужное действие. | все |
| `gitum sync [--to REF \| --next-release] [--layer L] [--step] [--candidate] [--publish]` | Каскадный перенос стека одним rebase на ref. Слой переносится, только если перенос родителя прошёл. `--step` — по коммиту, для bisect. | робот, ALT |
| `gitum continue \| skip \| abort` | Продолжить, пропустить или откатить незавершённый sync. Отказ откатывает весь стек атомарно. | все |
| `gitum accept` | Опубликовать кандидата после ревью (в том числе с правками кандидата на GitLab). | робот |
| `gitum publish` / `gitum pull` | Публикация. Pull забирает журнал и ветки коллег; их новые коммиты встают в слой сами. | все |
| `gitum save [series]` | Записать текущие ветки (слой или серию) в журнал. Обобщение `update`. | все |
| `gitum checkout <layer\|series[@base]> [--state S]` | Материализовать ветку из журнала, в том числе прошлое состояние. Обобщение `restore`. | все |
| `gitum series new\|list\|show\|set\|port` | Серия как сущность. `port <s> --to etersoft` переносит вариант на другую базу и показывает range-diff и расхождение. | kloder |
| `gitum check-upstream [series\|change]` | Поиск принятия: patch-id, затем subject и автор, затем нечёткое сравнение диффа. Вывод: «принят как <sha> с правками (87%)», «не найден» или «сомнительно» (код 2, нужно подтверждение). | все |
| `gitum queue [next] [--format md]` | Очередь в апстрим: порядок, зависимости, правило «один за раз». Генерирует `UPSTREAM-QUEUE.md`. | kloder |
| `gitum prepare <series> [--push fork]` | Rebase на свежий master с `--reset-author-date`, проверка чистоты, удаление trailer'ов, проверка заголовков, push в форк. MR создаёт человек. Для vendored — перераскладка путей (`--directory`/`-p`). | kloder, ALT |
| `gitum backport <url\|sha>… --into L [--series S]` | Бэкпорт с `Origin:` и судьбой `backport`. Изменение выбрасывается само, когда новая база содержит исходный коммит: проверка предка, а не patch-id. | все |
| `gitum forge refresh \| import-json \| export-json` | Состояния MR/PR: плагины GitLab, GitHub, Forgejo или JSON от внешних агентов (Lavtomate MCP). | все |
| `gitum log <change\|series>` | История через все версии апстрима: появился, менялся при конфликтах (кем разрешён), принят или выброшен. | все |
| `gitum diff <state1> <state2>` | range-diff между состояниями журнала по слоям и сериям. | все |
| `gitum export <layer\|series> --format staging\|quilt\|spec` / `gitum import …` | Каталог патчей (wine-kloder/patches/<серия>/), RPM, wine-staging. `--check` проверяет, не устарела ли копия. | все |
| `gitum branches` | Форки и PR-ветки по изменениям; устаревшие после merge или close. | ALT, kloder |
| `gitum locks` | Кто какую серию или слой держит: сессия, pid, хост, время. | все |

Коды возврата:
- 0 — успех (с `--detailed-exitcode`: 0 нет изменений, 10 обновлено);
- 1 — ошибка;
- 2 — нужен человек (конфликт, ревью, сомнительное принятие);
- 75 — занято, блокировка (как `REPOLOCK_BUSY_RC` у робота).

## 7. Движок sync

1. **Блокировка.**
   - `flock` на `$GIT_COMMON_DIR/gitum/lock` для операций со стеком;
   - файлы `gitum/locks/<серия>` с владельцем для серий;
   - незавершённый ручной перенос моложе суток робот не трогает.
2. **Снимок.**
   - Запомнить все затрагиваемые ссылки.
   - Работа идёт в **приватном linked worktree**
     `$GIT_COMMON_DIR/gitum/wt/<op>`: ни одного `reset --hard` или `clean`
     в чужом рабочем дереве.
   - Если обновляемая ветка checked out в чьём-то worktree, sync её не
     трогает и сообщает об этом (переопределяется флагом).
3. **Подготовка слоя.** Схлопнуть пары «патч + Revert» (точное совпадение
   subject, как в `annihilate-reverts.sh`).
4. **Классификация до переноса.** Для каждого изменения слоя относительно
   новой базы:
   - `dropped-upstream`: patch-id найден в `old_base..new_base` (`git cherry`);
   - `dropped-backport`: `Origin`-коммит — предок новой базы;
   - `dropped-marked`: судьба fixed-differently или disabled на этой версии;
   - остальное переносится.
5. **Перенос** одним проходом cherry-pick на новую базу (`--to` тег или
   commit). При конфликте работает цепочка разрешения:
   - rerere: общий `rr-cache` из журнала копируется в `rr-cache` репо до
     переноса и объединяется обратно после;
   - правила;
   - агент;
   - иначе стоп, код 2.

   Каждое разрешение записывается: изменение, файлы, резолвер, дифф
   разрешения. Если патч стал пустым, он классифицируется как
   `merged-modified?` (подтверждается через `check-upstream`).
6. **Сужение (опция).** При конфликте бинарный поиск по `old_base..new_base`
   находит апстримный коммит, после которого патч перестал ложиться. Это
   попадает в отчёт.
7. **Каскад.** Следующий слой переносится на новую вершину родителя.
8. **Проверка.** `publish.check` (сборка).
9. **Фиксация.**
   - Атомарно: `git update-ref --stdin` с проверкой старых значений (CAS)
     обновляет все ветки, коммит журнала и коммиты истории.
   - При любой ошибке ссылки не меняются; неудачное состояние сохраняется
     в `refs/gitum/failed/<run>` для разбора.
   - Режим `--candidate` пушит в `candidate/*` вместо публикации.
10. **Отчёт.**
    - `runs/<id>/report.json` в журнале: классификация по каждому изменению,
      range-diff по слоям, резолверы, сужение.
    - Человекочитаемая сводка (опционально HTML).
    - Хуки на каждое событие, например комментарий в eterbug.
11. **Перед публикацией.** Если ветка на origin изменилась (коллега добавил
    коммит), новые коммиты встают сверху (как `integrate_new_commits`);
    если история переписана — код 2.

## 8. Чего не будет

- gitum не создаёт MR/PR сам: только подготовка и push в форк.
- Нет своей системы сборки и уведомлений: только хуки.
- Не заменяет git: ветки остаются обычными ветками, gitum лишь
  синхронизирует их с журналом.

## 9. План

Порядок выбран так, чтобы каждый этап давал пользу сразу и робот
wine-rebased мог перейти на gitum как можно раньше.

**Этап 0. Фундамент.**
- Обёртка над git: subprocess, явные `cwd`/env на worktree. GitPython
  убираем, см. вопросы.
- Приватные worktree, транзакции ссылок, блокировки.
- Коды возврата, `--json`, каталог логов прогона.
- `gitum.toml`, формат журнала.
- `gitum init/import` из существующих веток и `-START` тегов.
- Тесты на всё это.

**Этап 1. sync (MVP для робота и для ALT).**
- Каскад слоёв, `--to`/`--next-release`, `--step`.
- Классификация (patch-id, бэкпорт, пустые, revert-пары).
- Цепочка резолверов с записью и общим rerere.
- Транзакционный откат и сохранение неудачного состояния.
- `candidate`/`accept`, `publish` с compat-тегами и версионными ветками,
  интеграция новых коммитов коллег.
- `report.json`, range-diff, хуки, сборка-проверка.
- Базовый `gitum status`.

После этого `update-rebased.sh` превращается в обёртку
`gitum sync --next-release --candidate --publish`. Слой staging пока
собирается внешней командой (`rebase-staging.sh` как генератор слоя).

**Этап 2. Изменения и серии.**
- `Gitum-Id`, метаданные и судьбы, `changes.json`.
- Серии и `definition` (импорт и экспорт staging).
- `gitum status` с деревом и таблицей «изменение → судьба → действие».
- `check-upstream` с нечётким сравнением, `log`, `diff`.
- Forge: JSON import/export и плагины GitLab/GitHub/Forgejo.

**Этап 3. Работа с апстримом.**
- Варианты серии на нескольких базах (`series port`, расхождение).
- Очередь и генерация `UPSTREAM-QUEUE.md`.
- `prepare`, `backport`, `branches`.
- Постоянные клоны апстримов вместо разовых в `~/tmp`.

**Этап 4. Упаковка.**
- Экспорт и импорт quilt/spec/staging.
- Нативный слой из серий staging (замена `rebase-staging.sh`).
- Gear/rpmgs (tarball-апстрим) и несколько апстримов с `prefix`.
- HTML-отчёт.

## 10. Принятые решения (2026-11-11)

1. Порядок этапов — как в разделе 9: фундамент, sync, изменения и серии,
   работа с апстримом, упаковка.
2. Ядро работает через тонкую обёртку над `git` (subprocess), без GitPython.
3. Python ≥ 3.11 (`tomllib`).
4. gitum 1 не поддерживается: ни его команды, ни перевод старых
   репозиториев на журнал.
5. Коды возврата: 0 успех (с `--detailed-exitcode`: 10 — обновлено),
   1 ошибка, 2 нужен человек, 75 занято.
6. Журнал — видимая ветка `gitum/journal`.

Уточнение при реализации: после rebase старые вершины слоёв перестают быть
достижимы из веток и пропали бы при `git gc`. Поэтому коммит журнала имеет
дополнительными родителями вершины слоёв. Основная линия журнала читается
через `--first-parent`, а любое прошлое состояние восстанавливается точно,
по исходным коммитам.

## 11. Состояние реализации (gitum 2.0.0)

Все этапы раздела 9 реализованы. Отличия от исходного проекта:

- **Идентичность изменений** хранится в журнале (`changes/<id>.json`), а не в
  trailer'е коммита. Изменение отслеживается по trailer'у `Gitum-Id`
  (если он есть), по соответствию sha при sync, по patch-id и по заголовку.
  Так удалось не переписывать сотни существующих коммитов.
- **Регенерируемый апстрим** (`rewritten = true` или `--allow-rewrite`):
  ветка вроде собранной patchinstall не продолжает свою прошлую версию.
- **Генерируемые слои** (`generator = "staging" | "command"`, плюс
  `post-command`) пересобираются, а не переносятся. На wine-rebased
  генератор staging воспроизвёл `rebased-11.20` робота, кроме `configure`,
  который генерируется другой версией autoconf.
- **Серия для vendored-дерева** имеет поле `upstream`, отдельное от базы:
  база лежит в истории приложения, а апстрим — другой репозиторий.
- **Параллельные сессии.** Разошедшиеся журналы сливаются при `pull` через
  `git merge-tree`, если менялись разные файлы. Одновременные изменения
  одного слоя или одной серии — код 2.

Проверка на реальных данных (клон wine-rebased): слои basealt (15 патчей)
и etersoft (156 патчей), перенесённые с 11.19 на 11.21, дали патчи,
идентичные результату робота (154 из 156; два отсутствующих робот позже
переделал). `check-upstream` нашёл принятый в wine-11.5 патч taskschd.
